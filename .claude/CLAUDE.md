# LightCycles

A local multiplayer Tron/lightcycles pass-and-play game (Expo/React Native, Skia-rendered). Part of the `@rific`/`@tastic`/InfiniteToken app ecosystem — depends on `@rific/auto-paper`, `@rific/feedback-press`, `@rific/focus-chain`, `@rific/splash-gate`, `@rific/toaster`, `@rific/updater`, `@tastic/achievements`, `@tastic/core`, `@tastic/edge-guard`, `@tastic/hud`, `@tastic/input`, `@tastic/profile`, `@tastic/split-screen`.

**Expo has changed.** Read the exact versioned docs at https://docs.expo.dev/versions/v57.0.0/ before writing any code — don't rely on general Expo knowledge, this app is on SDK 57 specifically.

## Tooling

Onboarded onto the shared `@infinitetoken` config packages (`eslint-config`, `jest-config`, `tsconfig`) — previously hand-rolled its own `eslint-config-expo`-based config, `jest-expo`-preset-direct config, and `expo/tsconfig.base`-extending tsconfig (the same pattern documented in [Swirlio](../Swirlio/.claude/CLAUDE.md)'s CLAUDE.md, which this migration followed).

`npx expo install --fix` + `npm update` were run as part of this pass too — confirmed clean: `npx expo install --check` reports up to date, `npm outdated` shows `Current === Wanted` for every dependency (remaining `Latest` values are all major bumps outside declared ranges, a deliberate-upgrade decision, not routine maintenance).

- `eslint.config.cjs` — `@infinitetoken/eslint-config/expo`, no local override
- `tsconfig.json` — `extends: "@infinitetoken/tsconfig/expo"`, keeps only the path-valued local bits (`paths`, `include`)
- `jest.config.cjs` — `@infinitetoken/jest-config/expo` with a `maxWorkers: '50%'` override (capping Jest's own CPU-count-minus-one default, which reliably triggers a "worker process has failed to exit gracefully" warning on this machine under multiple concurrent dev sessions) — `jest.setup.cjs` and `roots` are both auto-detected/defaulted (see below)

**`jest.config.ts` became `jest.config.cjs`, matching every non-Expo project in the fleet — no more `ts-node` gotchas.** This app (like every other Expo app) originally had `jest.config.ts` while every library/kit package used `.cjs` — a real divergence, not a justified one. `.ts` needed `import type {Config} from 'jest'` + a typed `const config: Config = ...` (a bare `export default createExpoJestConfig(...)` fails `tsc`'s declaration-emit check), plus a separate non-extending `tsconfig.jest.json` wired in via `TS_NODE_PROJECT=./tsconfig.jest.json` on `test`/`test:watch` (`ts-node`, Jest's `.ts`-config loader, can't resolve a tsconfig `extends` through a package's `exports` map at all). None of that exists for `.cjs` — plain `require()`, no transpilation, nothing to typecheck. Converting removed `tsconfig.jest.json`, the `TS_NODE_PROJECT` prefix on both scripts, and the `ts-node` devDependency entirely — see `@infinitetoken/jest-config`'s own README ("Why `.cjs`, not `.ts`") for the full history.

**`prettier.config.js` was deleted — `package.json` now has `"prettier": "@infinitetoken/eslint-config/prettier"` instead**, same as every library/kit package. The local file was a byte-for-byte duplicate of the shared package's own `prettier.cjs`; every Expo app had independently copy-pasted it rather than referencing the shared one.

**`metro.config.js` was deleted — it was unmodified `getDefaultConfig(__dirname)` boilerplate doing nothing.** Confirmed by removing it and running `npx expo export -p web`: builds cleanly, `canvaskit.wasm` still lands in `dist/` (copied into `public/` by the `setup-skia-web` postinstall script and served as a static file, fetched at runtime by `canvaskit-wasm`'s own init code — never `require()`d through Metro's bundler, so `resolver.assetExts` is irrelevant to it regardless). Swirlio never had this file at all and works the same way — this file's presence elsewhere in the fleet is boilerplate carried over from `expo customize`, not a requirement.

**Native/Expo module mocks moved from inline `jest.mock()` calls in `jest.setup.cjs` into individual `src/__mocks__/*.ts` files** — `react-native-reanimated`, `react-native-worklets`, `@expo/vector-icons` (+ its `createIconSet` deep import), `expo-splash-screen`, `expo-sensors`, `react-native-gesture-handler`, `react-native-safe-area-context`, `expo-router`. This is a fleet-wide convention change, not LightCycles-specific — see `@infinitetoken/jest-config`'s own CLAUDE.md for the full reasoning. `jest.setup.cjs` now holds only genuine setup-file content (the `IS_REACT_ACT_ENVIRONMENT` flag, `unhandledRejection`/`uncaughtException` handlers, the RAF/cancelAnimationFrame polyfills, and the no-factory `NativeAnimatedHelper` automock) and is auto-detected by `@infinitetoken/jest-config/expo` — no `setupFilesAfterEnv` option needed at all. Also renamed from `.ts` to `.cjs` — a later, separate cleanup: auto-detection genuinely supports either (a `.ts` setup file goes through Jest's own test transform same as any other `setupFilesAfterEnv` entry, unlike `jest.config.cjs` itself, which Jest loads directly before any transform exists), but once its content shrank to thin boilerplate with the mock factories gone, there was no remaining reason for this one hand-authored config file to use a different extension than every other one in the app — see `@infinitetoken/jest-config`'s README, "Why `.cjs`, not `.ts`." With the mock factories' `any` usage gone, `jest.setup.cjs` no longer needs its own `no-explicit-any` eslint override — `eslint.config.cjs` is back to the plain one-liner. The one remaining `any` in `jest.setup.cjs` (bridging `requestAnimationFrame`'s polyfilled `NodeJS.Timeout` return type into `cancelAnimationFrame`'s DOM-lib `number` signature) is a single targeted `eslint-disable-next-line`, not a file-wide exemption.

**One standing exception to "no `jest.mock()` call needed" (see Testing below): a *subpath* import.** Jest's manual `__mocks__` auto-pickup only ever matches a bare package specifier, never a deep import — confirmed empirically, not just in this repo (see Hangman's own `jest.setup.cjs`). `jest.setup.cjs` currently registers two: `@expo/vector-icons/createIconSet` (factory-less, delegating to `src/__mocks__/@expo/vector-icons/createIconSet.ts` — the mock content did move out as described above, but Jest still needs the explicit call to know to use it) and `@rific/feedback-press/audio` (inline factory, no adjacent `src/__mocks__/` file at all, since the stub is one line). Both are commented in place with the same reasoning; add a new one the same way if another subpath import ever needs mocking, rather than trying to force it through the bare-specifier auto-pickup path.

**The `modulePathIgnorePatterns: ['<rootDir>/.claude/worktrees/']` `overrides` entry this app previously needed is gone too, and not because it was removed by hand.** `@infinitetoken/jest-config/expo` now defaults `roots: ['<rootDir>/src']` (see its own CLAUDE.md — added specifically to make `src/__mocks__/` the manual-mock pickup location instead of the repo root). Since `.claude/worktrees/` lives outside `src/`, Jest's haste map scan never reaches it anymore either — confirmed directly: removing the override entirely and running the full suite produces no `jest-haste-map: Haste module naming collision` warning, with an active worktree still checked out in this repo. The `roots` default fixed this as a side effect, not the motivation for adding it.

## Drift audit and shared-package extraction (2026-09-17)

A fleet-wide audit today compared this app against its 4 siblings (AirHockey, BoxHockey, Pong, Snake) and found this app had drifted the most of the five — several real, app-specific bugs, all fixed below — plus pulled four pieces of now-duplicated code out into shared packages. Everything in this section is real, already-verified, uncommitted work in this repo's working tree, not a plan.

**Missing error-toast wiring.** This app had no `src/components/UpdateDialog.tsx` bridge at all — `_layout.tsx` imported and rendered `@tastic/hud`'s own `UpdateDialog` directly, with no `onError`, so an update-check failure (bad network, malformed manifest, etc.) was silently swallowed instead of surfaced. `SettingsDialog.tsx`'s `BaseSettingsDialog` had the identical gap on its own manual "Check for Update" path. Fixed by adding `src/components/UpdateDialog.tsx` — a thin bridge that calls `useToast().error('Update check failed', message)` from `@tastic/hud`'s `UpdateDialog`'s `onError`, same shape as AirHockey's/BoxHockey's/Pong's/Snake's own file of that name — and wiring `SettingsDialog.tsx`'s new `onUpdateError` prop the same way. Matches the fleet convention every sibling app already had; this app was the outlier.

**Root status bar ignored Lock Orientation.** `_layout.tsx`'s local `RotationAwareStatusBar` called `useOrientationState()` with no argument, so the real OS status bar's hide/show always tracked live device tilt regardless of whether the user had Settings' Lock Orientation toggle on. Fixed by threading `settings.lockOrientation` through, matching AirHockey's/BoxHockey's/Pong's/Snake's identical usage — then immediately superseded by the extraction below, which moved the component itself out of this app entirely.

**No settings/profiles splash gates.** Unlike AirHockey/BoxHockey/Pong, this app read `useGameSettings()`/`useProfiles()` immediately at mount with nothing waiting for their AsyncStorage/shared-App-Group-store reads to resolve — a cold-start race risking a flash of `DEFAULT_SETTINGS` or a stale/empty profile roster before the real values land. Fixed by adding `'settings'`/`'profiles'` gates to `src/utils/splashGate.ts` (now also exports `Gate: SplashGate`), a `loaded` field to both `GameSettingsProvider` (`useGameSettings.tsx`) and `ProfilesProvider` (`useProfiles.tsx`), and `SettingsGate`/`ProfilesGate` wrapper components in `_layout.tsx` — nested *inside* their respective providers' own position in the tree, not wrapping the providers from the outside, since an outside gate would deadlock (a provider blocked from mounting can never run the read that would flip its own `loaded` flag). Mirrors the other 3 apps' pattern exactly.

**Settings AsyncStorage all-or-nothing wipe (shared with 3 sibling apps).** `useGameSettings.tsx`'s stored-settings validation ran `isValidSettings` straight against the raw parsed blob, with no partial-merge path — so a blob saved before some `GameSettings` field existed was missing that field entirely, failed validation wholesale, and silently reset *every* other still-valid preference in it the moment a new field shipped. Fixed by merging the parsed blob onto `DEFAULT_SETTINGS` before validating: an old blob now only loses the field(s) it genuinely predates, and a field it does provide with the wrong type still rejects the merge exactly as before.

**`Theme.tsx` marked its `'theme'` splash gate ready immediately instead of waiting for `AutoPaperProvider`'s own `onReady`.** Found while auditing BoxHockey's identical bug: this app's `Theme.tsx` called `useSplashReady('theme', true)` unconditionally right after reading the Redux `theme` slice, reasoning that `PersistGate` already resolving `settings` was enough — but `AutoPaperProvider` itself still renders `null` internally until it's actually computed a theme object from that settings value, a separate, later step. Marking the gate ready before that could let the splash screen lift while `AutoPaperProvider` was still rendering `null` underneath it. Fixed to match AirHockey's/Pong's own `Theme.tsx`: `const onReady = useCallback(() => markSplashReady('theme'), [])` passed to `<AutoPaperProvider onReady={onReady}>`.

**Face-to-face achievement toast rotation — the reference, not a fix.** This app's `profileUnlockToast` state (`game.tsx`), threaded into `RoundOverDialog`/`MatchOverDialog` as per-seat achievement badges correctly oriented per seat, was never broken here — it's the pattern BoxHockey's/Pong's/Snake's own equivalent fixes this session were modeled on. Nothing changed in this app for this item; noted here only so the drift audit's scope reads as complete.

**A sixth, LightCycles-only fix found while auditing this repo (not part of the fleet-wide comparison above): a lobby seat's manual color override on a profile-selected seat didn't survive navigation.** `lobby.tsx`'s `handleSeatColorChange` used to skip persisting anything for a seat currently tethered to a profile (see `persistSeatColor`'s own doc), which meant a manual recolor or clash-swap on that seat was nothing more than whatever the `theme` slice happened to already be showing — no persisted state behind it at all. The very next mount of this screen (leaving and coming back, not just a real profile reselect) had nothing to fall back on except the mount/reapply effect's own unconditional `profile.color`, so the override silently vanished. Fixed 2026-09-16 per Jay's original ask that "profile colors & overrides... are persisted for relaunch": added a `profileOverride: Record<Player, string | null>` field and `setProfileOverride` action to `seatColorsSlice.ts` (persisted via the same `redux-persist` setup as `lastGuestColor`/`lastCpuColor` — see `store.ts`), had `persistSeatColor` write into it instead of skipping, and had the mount/reapply effect resolve a profile-selected seat's target color as `profileOverride[seat] ?? profile.color`. The override is cleared in exactly one place — `handleP1ProfileSelect`/`handleP2ProfileSelect`, i.e. that seat's selection genuinely changing — never by this screen merely remounting.

Six duplicated pieces of code across this app and the same 4 siblings were extracted into shared packages today, and this app was migrated to consume them across five packages: `@rific/feedback-press`, `@tastic/achievements`, `@tastic/core`, `@tastic/hud`, and `@tastic/profile`.

- **`RotationAwareStatusBar`** moved from the local function in `_layout.tsx` (see above) into `@tastic/core` itself. `_layout.tsx` now renders it through a thin `AppRotationAwareStatusBar` wrapper that just resolves `settings.lockOrientation` and passes it through — same shape as the other 4 apps.
- **The staggered-letter hero wordmark animation** — `AnimatedHeroTitle.tsx`'s local `AnimatedLetter`/`Word` components and their `STAGGER_MS`/`LETTER_DURATION_MS` constants — moved into `@tastic/hud`'s new `StaggeredWord` component and `getStaggeredWordDuration` helper. The custom `CYCLES_VERTICAL_OFFSET` geometry (the deliberate vertical overlap between the "Light" and "Cycles" wordmarks) was preserved exactly; only the letter-stagger mechanism itself was replaced.
- **The Redux-backed `FeedbackBridge`** in `Providers.tsx` now builds its `FeedbackPressProvider` props via `@rific/feedback-press`'s new `useFeedbackBridgeProps` hook instead of wiring `initialValue`/`onChange`/`soundInitialValue`/`onSoundChange`/`sound` by hand.
- **`src/utils/achievementEngine.ts`** shrank to a thin re-export via `@tastic/achievements`' new `createAchievementBindings(ACHIEVEMENT_CATALOG, getProfileStatsView)` factory — same three exported names (`evaluateUnlockedIds`, `evaluateUnlockedIdsForProfile`, `unlockedKey`), so no call site needed to change.
- **`src/redux/profileSelectionSlice.ts`** shrank to a thin re-export via `@tastic/profile`'s new `createProfileSelectionSlice<Player>('lightcycles', defaultProfileSelectionState)` factory — same exported names (`profileSelectionActions`, default reducer).
- **`PlayerSetupPanel`** — see below; migrated in a later pass the same day, once the panel itself existed as a shared `@tastic/hud` component.

**`src/hooks/useZoneClampedAlign.ts` — deleted, migrated to `@tastic/hud`'s new shared `useZoneClampedAlign`, a verbatim port.** This app originated the hook (a `useAutoAlign` wrapper that clamps a rotation-aware popover's alignment to whichever zone of a `DualZoneLayout` it's actually rendering in, so it doesn't visually overlap the opposite player's half); the fleet-wide audit found the other 4 apps wanted the identical behavior but had no equivalent of their own, so it moved into `@tastic/hud` (a new peer dependency on `@tastic/split-screen` + `react-native-safe-area-context`, both already real dependencies of this app) rather than staying LightCycles-only. No behavior change here — this app's own call sites just import it from `@tastic/hud` now instead of `@/hooks/useZoneClampedAlign`.

**`src/components/LobbyPlayerPanel.tsx` — deleted, migrated to `@tastic/hud`'s shared `PlayerSetupPanel` in a later pass the same day.** The exception noted above (this file hand-rolling its own version rather than adopting the shared component, unlike the other 4 apps) was resolved once the drift-audit changes above had settled: `lobby.tsx` now renders `@tastic/hud`'s `PlayerSetupPanel` directly, with the key-scheme picker (formerly `LobbyPlayerPanel`'s own `KEY_SCHEME_OPTIONS`/`SectionedDropdown`, now moved into `lobby.tsx` itself) passed in via the panel's generic `secondPicker`/`secondPickerId` slot — same pattern as AirHockey's/BoxHockey's/Pong's own `loadout.tsx`. `handleP1ProfileSelect`/`handleP2ProfileSelect` preserve this app's own pre-fill behavior (selecting a profile also applies its saved key scheme) that `LobbyPlayerPanel` used to own internally.

**A live browser check of AirHockey's `/loadout` screen (its migration this same round is byte-for-byte the same shape as this app's own) turned up a real bug in `@rific/core`, upstream of this app's own `Theme.tsx`/`GameSettingsProvider`/`OrientationProvider`.** `createSettingsContext`'s `set()` called the consumer's `onChange` *inside* the `useState` updater passed to `setSettings` — a `useState` updater must be pure, since React can invoke it outside the originating `set()` call (e.g. replaying a queued update while resolving a later render of the very same Provider), and when that happened, `onChange` (which `Theme.tsx` wires straight to `dispatch(themeActions.initialize(...))`) fired synchronously mid-render of an unrelated component — a genuine "Cannot update a component while rendering a different component" React warning. This factory backs `@rific/auto-paper`'s `Theme`, `@rific/feedback-press`'s haptic/sound settings, and `@rific/scroll-view`'s settings context alike. The same audit found the identical shape independently duplicated, not through this factory, twice more inside `@tastic/core`: `createGameSettingsProvider`'s `setSettings` called `AsyncStorage.setItem` from inside its own updater, and `OrientationProvider`'s `set` called the consumer's `onLockChange` the same way — both used by this app. All three were fixed the same way: the side effect moved into a `useEffect` keyed on the settled state, skipping the mount-time run so the contract (onChange/persistence only fires for a real `set()` call, never for `initialValue`/`defaultSettings` seeding) is unchanged. Now on `@rific/core@0.1.2` and `@tastic/core@0.5.1` (both patch bumps, no API change) — this app's own `npm run verify` (415/415 tests) stayed green through the bump.

**Same pass also found and fixed a real gap in `@infinitetoken/jest-config`'s `knownSubpathMocks`:** it stubbed `@rific/feedback-press/audio`'s `useAudioPool` but not `useGatedAudioPool` — a real risk for this app specifically, since `hooks/useGameSound.ts` re-exports `useGatedAudioPool` directly, and any future test rendering a component that calls it would have hit real `expo-audio`/native audio APIs during a Jest run instead of the intended inert stub. Fixed by adding the same inert-hook stub for it. Now on `@infinitetoken/jest-config@0.3.1`.

**`@tastic/hud`'s `PlayerSetupPanel` gained `colorAlignOverride`/`cpuDifficultyAlignOverride` props (v0.9.0), closing the exact gap this app's own `p2Panel` comment (see above) used to document — 4 sibling apps' own migration agents had independently found they couldn't wire `useZoneClampedAlign` (which this app originated) into `PlayerSetupPanel`'s internal CPU-difficulty `LabeledDropdown` for lack of any override prop.** `lobby.tsx` now wires `cpuDifficultyAlignOverride` for `p2Panel` anyway, for consistency with every other popover in this app, via `useZoneClampedAlign(p2CpuDifficultyOpen, LABELED_DROPDOWN_POPOVER_WIDTH, getLabeledDropdownContentHeight(CPU_DIFFICULTY_OPTIONS.length))` — `p2CpuDifficultyOpen` reads `p2Host.openId === getCpuDifficultyPopoverId('p2')` (the new `getCpuDifficultyPopoverId` export exists specifically so a caller doesn't have to hardcode `PlayerSetupPanel`'s own internal id-naming convention). This is still a confirmed no-op for this app specifically, same conclusion as before this prop existed: the CPU-difficulty picker only ever renders for a non-human seat 2 (vsCpu-only), and vsCpu always renders in the plain stacked, non-`DualZoneLayout` branch below — `useZoneBounds()` is null there regardless, and `useZoneClampedAlign`'s own doc says it returns `useAutoAlign`'s plain result unchanged whenever that's the case.

**`assets/sounds/countdown-go.wav`/`countdown-tick.wav` renamed to `countdownGo.wav`/`countdownTick.wav` (2026-09-17), matching BoxHockey's camelCase convention for a multi-word own-SFX filename (`faceoffGo.wav`, `wellAttract.wav`, ...) instead of kebab-case — a real, if cosmetic, naming fork the fleet-wide audit flagged and Jay asked to converge on camelCase everywhere.** Only `src/components/OnboardingOverlay.tsx`'s two `require('../../assets/sounds/countdown-tick.wav')`/`require('.../countdown-go.wav')` calls referenced the old names — updated to match. Every other sound asset in this app (`crash.wav`, `draw.wav`, `notification.wav`, `select.wav`, `turn.wav`, `win.wav`) was already a single word, so this pair was the only fork here. Confirmed clean via `npm run verify` (415/415 tests) and a live web reload (Metro's own bundler would fail to resolve a stale `require()` path immediately on any screen load, not just when `OnboardingOverlay` itself renders — no error either way).

## Fleet-wide drift audit round 3 (2026-09-18)

A third fleet-wide scan found a real bug in `lobby.tsx`: **`colorAlignOverride` was never wired to either color picker, even though `PlayerSetupPanel`/`InlineColorPicker` already supported it (the same plumbing `cpuDifficultyAlignOverride` uses).** Unlike the CPU-difficulty picker (a confirmed no-op everywhere in the fleet), both p1's and p2's color pickers genuinely render inside a live `@tastic/split-screen` `DualZoneLayout` zone in two-player mode, so an unclamped popover could overflow past the zone's shared-row boundary into the other player's half. Fixed by computing `colorContentSize` once via `@tastic/hud@0.9.1`'s new `getInlineColorPickerContentSize(defaultColors.length, windowWidth)` (see that package's own CLAUDE.md), then a `p1ColorAlign`/`p2ColorAlign` pair via `useZoneClampedAlign`, mirroring `cpuDifficultyAlign`'s own shape — checked against `getColorPopoverId('p1'|'p2')` instead of `getCpuDifficultyPopoverId`. Wired unconditionally for both seats. `npm run verify` (415/415 tests) stayed green.

## Fleet package extraction round 2 (2026-09-18)

Eight more pieces of duplicated fleet code were extracted into shared packages today, and this app was migrated onto all six updated packages — `@rific/core` (now 0.1.4, yalc-linked, replacing the prior `^0.1.1` range), `@tastic/achievements` (0.1.2, replacing `^0.1.1`), `@tastic/hud` (0.11.0, replacing `^0.8.4`), `@tastic/profile` (0.6.0, replacing `^0.4.0`), `@tastic/core` (0.7.0, replacing `^0.5.0`), and `@rific/auto-paper` (0.11.1, replacing `^0.11.0`) — versions per `yalc.lock`. None of these eight swaps touched a file this app actually has dedicated test coverage for: `src/__tests__/` only covers pure engine/hook/validation logic (`achievementEngine`, `statsEngine`, `useGameState`, `useProfiles`, etc.) — there is no `_layout.test.tsx`, `Theme.test.tsx`, `game.test.tsx`, `achievements.test.tsx`, or `profiles.test.tsx` in this app at all (unlike Snake's own `Theme.test.tsx`, which mocks `@rific/auto-paper` and needed that mock updated for the identical theme-bridge swap below) — so none of the eight required a test/mock update on this side.

- **`safeBack`** (`src/utils/navigation.ts`) now binds to `@rific/core`'s own shared `safeBack` instead of a locally hand-rolled implementation. The file shrank to a 5-line shim: `configureNavigation({ router })` (injecting expo-router's real `router` once, at module load) followed by `export { safeBack }`. `@rific/core` itself never imports `expo-router` — it's kept as an optional peer dependency (`peerDependenciesMeta.optional: true`), mirrored locally as a hand-written 3-method `SafeBackRouter` type (`canGoBack`/`back`/`replace`) rather than `typeof import('expo-router')`, so a future consumer with no interest in navigation isn't forced to install or type-resolve the real package. `safeBack()` stays deliberately zero-argument, reading the injected router back out of module-level config instead of taking it as a parameter — the one hard constraint that survived extraction, since every call site in this app (`onBack={safeBack}`, `onExit={safeBack}`, `onConfirm={safeBack}` in `game.tsx`/`profiles.tsx`) passes it as a bare callback reference, not a wrapped closure. No Provider component exists for this (unlike `@rific/core`'s Scanner-style factories) — `configureNavigation` runs once at import time, well before any component that calls `safeBack()` from an event handler has mounted, so there's no first-render ordering hazard a Provider would need to solve.

- **Achievement state pipeline** (`src/hooks/useGameStats.tsx`, `src/app/game.tsx`) now runs through `@tastic/achievements`' new `mapUnlocksBySeat`/`broadcastDeviceUnlocks` instead of this app's own hand-rolled seat-translation loop and broadcast block. `useGameStats.tsx`'s `recordRoundOutcome` calls `mapUnlocksBySeat([1, 2] as Player[], context.profileIds, result.profiles)` to translate `useAchievements`' profile-id-keyed unlock map back into the seat-keyed shape `game.tsx` actually consumes (the package itself has no notion of seats). `game.tsx`'s two-player branch of `handleRoundOutcome` calls `broadcastDeviceUnlocks([1, 2] as Player[], result.profiles, result.device)` to fan a device-wide/"All Profiles" unlock into both seats' own `profileUnlockToast` entries, since neither seat owns it more than the other. Both are pure, seats-as-a-parameter functions with no rendering of their own, so this was a drop-in for this app — order is preserved (a seat's own profile-scoped unlocks still land before the broadcast ones in the concatenated array). The vsCpu branch (a single flattened `[...result.device, ...(result.profiles[1] ?? [])]` merge into `@rific/toaster`'s toasts) was untouched, since that shape was never duplicated fleet-wide.

- **Quit confirmation** (`src/app/game.tsx`) now uses `@tastic/hud`'s `useQuitConfirmation(hasProgress, onConfirmedBack)` in `GameRound`, in place of this app's own `useState`+handler pair. **This app is on the hook's corrected, lazy `() => boolean` signature** — the call site is `useQuitConfirmation(() => roundHistory.length > 0, safeBack)`, not a plain boolean. That correction exists upstream because `paused` (derived from the hook's own `confirmVisible`) has to be computed and handed to `useGameState()` *before* that call returns the very state (scores/lives/bricks) a plain-boolean `hasProgress` would need to read — a real circular render dependency in AirHockey/BoxHockey/Pong (`paused` → `useGameState` → state → `hasProgress` → `confirmVisible` → `paused`), which all three had independently patched around with their own one-commit-behind shadow state before `@tastic/hud`'s `useQuitConfirmation.ts` fixed the hook's own contract with a lazy getter read at `requestBack`-call time instead. **LightCycles never had that circular dependency and needed no workaround of its own to adopt the corrected signature**: confirmed by grep, neither `useGameState.ts` nor `game.tsx` has a `paused` parameter or concept anywhere — this app's game loop simply never gates on `confirmVisible`/`settingsOpen` in the first place. So wrapping `roundHistory.length > 0` in a lazy arrow here was a trivial one-line adaptation, not a fix for anything broken on this side. That said, the gap this implies is real and still open: the round can keep ticking visually behind the "Quit Match?" (or Settings) dialog, since there's no `paused` wiring anywhere in this app to stop it — a pre-existing, unrelated issue worth its own follow-up, not something this migration touched or was meant to fix.

- **Achievements scaffolding** (`src/app/achievements.tsx`) now computes its catalog rows via `@tastic/achievements`' `getAchievementCatalogRows(ACHIEVEMENT_CATALOG, stats, statsView, unlockedAchievements, effectiveProfileId)` and renders them through `@tastic/hud`'s `<AchievementCatalogSection rows={...} />`, with the ACTIVITY block replaced by `<ActivityStatSection stats={statsView} />`. This deleted the local `MS_PER_DAY`/`startOfDay`/`unlockedLabel` day-diff formatter, the `ACHIEVEMENT_CATALOG.map(...)` loop, and the `<StatSection label='ACTIVITY'>` block outright — all three were byte-identical (modulo comments) across all 5 apps. Everything else on this screen (`OVERALL`, `VS CPU`, `TWO PLAYER (LOCAL)`, `COLORS (W-L-D)` with its local `ColorStatRow`, and `PLAYER RANKINGS` with `ProfileRankingRow`) stayed exactly as it was — those sections' own metrics are genuinely LightCycles-specific and were correctly left out of the extraction's scope. **`@tastic/hud`'s `AchievementCatalogSection` briefly had its own locally-duplicated `AchievementCatalogRow` type**, built before `@tastic/achievements` had actually shipped `catalogRows.ts` — confirmed that's since been corrected: `AchievementCatalogSection.tsx` now imports the real `AchievementCatalogRow` type from `@tastic/achievements` as a genuine, type-only peer dependency (`@tastic/achievements": ">=0.1.2"` in `@tastic/hud`'s own `package.json`), with a doc comment there noting the two shapes were checked to match before the switch — not the transient workaround state. `ACHIEVEMENT_TIER_COLORS`/`unlockedKey` still come from this app's own `@/constants/achievements`/`@/utils/achievementEngine` re-exports unchanged, and the "ALL ACHIEVEMENTS" label's `MONO_FONT` styling moved entirely into `@tastic/hud`'s component.

- **Profiles screen** (`src/app/profiles.tsx`) is now a thin route wrapping `@tastic/profile`'s new `ProfilesScreen` component instead of hand-rolling the container view, back button, and `ProfilesManager` ref/`commitPendingEdit()`-before-navigate composition locally. The route shrank to reading `useProfiles()`/`useGameStats()` and passing their values straight through as props — `ProfilesScreen` itself never calls either hook (both are app-local and genuinely differently-shaped per app), staying props-in/callbacks-out exactly like `ProfilesManager` underneath it. This app needed the same two adaptations it already needed calling `ProfilesManager` directly, both still present and unaffected by the extraction: `onCreate` composes `{ ...patch, keyScheme: NEW_PROFILE_KEY_SCHEME }` (this app's `createProfile` takes a locally-widened `CreateProfileInput` with a required `keyScheme` field, not `@tastic/profile`'s base `{name,color,tag}` shape), and `defaultColor` is passed as this app's own `DEFAULT_P1_COLOR` constant from `@/constants/game.ts` rather than `@rific/auto-paper`'s `defaultColors[0].value` the other 4 apps pass — a genuine, pre-existing divergence, not an oversight to converge away, and exactly why `ProfilesScreenProps.defaultColor` is a plain required string rather than something the component defaults internally.

- **Layout corner flash** (`src/app/_layout.tsx`) now gets its root `<Stack>`'s screen options from `@tastic/core`'s `useThemedRootBackground(dark, false)` instead of a locally hand-rolled `useEffect`+`expo-system-ui` call paired with an inline `screenOptions` object literal. The hook bundles both halves of the fix every app needed — the module-load-time `SystemUI.setBackgroundColorAsync('#000000')` first guess, plus a `useEffect` that corrects it to `'#000000'`/`'#FFFFFF'` on every `dark` change — and returns `{ headerShown, gestureEnabled, contentStyle }` as one plain object for `AppStack`'s `<Stack screenOptions={...}>` (this is what stops react-native-screens' push/pop transition from flashing the OS's default white root-window background through the display's rounded corners). `gestureEnabled` is deliberately still a parameter the hook doesn't hardcode — it addresses the unrelated problem of iOS's native swipe-back gesture fighting `TouchInputLayer`'s own swipe-to-turn Pan gestures on `/game`, not corner-flash — so this app kept its own real, on-device-confirmed rationale comment for passing `false`, just repositioned to sit above the `useThemedRootBackground(dark, false)` call instead of above an object-literal field.

- **SplashGate wrapper** (`src/app/_layout.tsx`) — the settings/profiles readiness gate now goes through `@tastic/core`'s `SettingsAndProfilesGate` instead of this app's own separately-named `SettingsGate`/`ProfilesGate` components. This was a real restructuring, not a body-only swap: those two components used to be nested at two different depths directly in `RootLayout`'s own JSX (`SettingsGate` wrapping everything from `GameStatsProvider`'s child down, `ProfilesGate` nested one level further in, under `ProfilesProvider`) rather than as adjacent siblings the way AirHockey's split version was. Both were deleted and replaced with one merged `GatedApp` wrapper — matching BoxHockey's/Pong's pre-existing single-component shape — that reads `settingsLoaded`/`profilesLoaded` off `useGameSettings()`/`useProfiles()` (both app-local hooks the shared component can't call itself) and renders `<SettingsAndProfilesGate Gate={SplashGate} settingsLoaded={...} profilesLoaded={...}>`, passing this app's own bound `SplashGate` (from `@/utils/splashGate`) in as the `Gate` prop rather than the shared package importing `@rific/splash-gate` itself. The pre-existing `GameSettingsProvider` → `GameStatsProvider` → `ProfilesProvider` ordering (`GameStatsProvider` sits between the two providers the gate actually cares about, unlike the other 3 apps) was left exactly as-is — orthogonal to the gate itself, per this file's own existing comment, and not something this migration touched.

- **Theme bridge** (`src/components/Theme.tsx`) now builds its `<AutoPaperProvider>` props via `@rific/auto-paper`'s new `useThemeBridgeProps({ initialValue, onChange, onReady })` instead of passing those three props directly. The `useSelector`/`useDispatch<AppDispatch>`/both `useCallback`s (`onChange` dispatching `themeActions.initialize`, and the one-shot `onReady` that marks the `'theme'` splash gate only once `AutoPaperProvider` itself reports ready — the exact bug this app and BoxHockey each hand-fixed independently in the 2026-09-17 drift audit above, before this hook existed) are all untouched, since `RootState`'s type and `markSplashReady`'s identity are both app-local and can't move into a shared package. This app keeps its own extra `reanimated={Reanimated}`/`fontFamily={MONO_FONT}` props appended after the `{...bridgeProps}` spread — neither is part of the bridge's contract, and both were already genuinely app-specific (LightCycles is the one app in the fleet injecting `reanimated`, the way Snake injects `expoBlur` instead). No test needed updating for this swap — this app has no `Theme.test.tsx` to begin with, unlike Snake's, which mocks `@rific/auto-paper` and had to add `useThemeBridgeProps` to that mock's factory to avoid breaking.

## How-to-play guide (2026-09-19)

A first-run, replayable "how to play" flow, built on `@tastic/hud/guide` (a light-peer subpath of `@tastic/hud`, so it works in apps without Skia/`@tastic/core`; see that package's own CLAUDE.md, "The guide subpath"). **Do not call any of this "onboarding"** — `OnboardingOverlay`, `GamePhase 'onboarding'` and `ONBOARDING_*` already mean the per-round 3-2-1-GO countdown; the how-to-play code is `guide` everywhere.

- **Content:** `src/constants/guideSteps.tsx`: `getGuideSteps({ touch, keys })`, three cards, pure and hook-free: Steer Your Cycle / Last One Riding Wins / Two Players, One Phone (or One Keyboard on desktop web). `keys` is the live `settings.keyScheme`, so the desktop copy and `DirectionKeysHint` caps name each seat's real keys (seats pick WASD/arrows/IJKL in the lobby), not the defaults. The desktop two-player card uses the fleet's shared wording: "Two Players, One Keyboard" / "Player 1 uses {A}, player 2 uses {B}. Change them before a match." (phrases from `KEY_PHRASE`: WASD, the arrow keys, IJKL). LightCycles has no mouse scheme, so it never gets the fleet's "One Computer" / "Drag in your own half." variant. Illustrations: `SwipeHint`/`DirectionKeysHint`/`SeatDiagram`/`SeatDevicesHint` (desktop two-player card, `devices={['keyboard', 'keyboard']}`) from `@tastic/hud/guide`, plus this app's own `GuideTrailCrash` in `src/components/GuideArt.tsx` (the only game-specific picture; don't redraw a shared one locally). Copy is what a first-timer can't work out alone (nothing here is printed in-game): steering is absolute, walls and any trail (your own included) are lethal, last cycle riding wins, two players share one phone face to face.
- **Copy rules (Jay, 2026-09-24):** Title Case titles, one-word buttons (the last card's is `Ready`), short bodies, and only say what's true in every mode ("your half" is only true in two-player, so it's on the two-player card, not the steering one). No card explaining One Player vs Two Player: those buttons are right behind the dialog. Don't mix "trail" and "tail" in one sentence.
- **Wiring:** `src/components/GuideHost.tsx` (Redux "seen" version + `useRotation` passed as `rotation` + the steps → `GuideProvider`), mounted in `_layout.tsx` around `<AppStack />`. Home (`index.tsx`) calls `useAutoShowGuide()` — Home only, so it can never fire over a live match or a two-seat lobby. Settings row: `SettingsDialog`'s `showHowToPlay` prop → `BaseSettingsDialog`'s `onShowHowToPlay`; on for Home and the lobby, **deliberately off for `/game`** (settings there pauses/overlays a live match).
- **Persistence:** `src/redux/guideSlice.ts` (a `createGuideSlice` binding) mounted as `guide` in `store.ts`. `GUIDE_VERSION` (`src/constants/guide.ts`) is what an existing player is stamped with: a persisted root store with no `guide` key means "had the app before this shipped", so they are **not** shown the guide after an OTA update; a fresh install rehydrates with no payload and sees it once. **Players from the shipped pre-redux build (7a595fa, otaVersion 13, 2026-09-12) are grandfathered by the migrate:** that build predates the redux-persist root store (added in 8094877), so those players have no root store and the slice alone would take them for a fresh install. `store.ts`'s `persistConfig.migrate` is `createReturningPlayerMigrate(AsyncStorage, LEGACY_STORAGE_KEYS)`; `LEGACY_STORAGE_KEYS` (exported from `guideSlice.ts`) is the nine `lightcycles.*` keys 7a595fa wrote, as literal strings read from that commit's source, not today's constants. No root store plus any of those keys means a returning player, rehydrated with an empty payload the slice stamps as seen. Never let anything write one of those keys before `PersistGate` opens (a provider outside `Providers.tsx`'s PersistGate, or module load): a fresh install would then be taken for a returning player. Today `lightcycles.settings`/`.stats`/`.achievements` are still written, but only from providers inside PersistGate. Only finish/skip writes; a replay never does. Bump `GUIDE_VERSION` only for a real controls/rules change: every player sees it again.
- **Not built yet:** a guided practice round against an easy CPU (the loadout's `commitRoundSettings({ ...vsCpu, cpuDifficulty: 'easy' })` pattern would launch it, but `game.tsx` records stats/achievements on every game over and would need a no-record guard first).
- **Tested:** `guideSteps.test.tsx` (content shape, touch vs desktop copy, the fleet two-player wording and `SeatDevicesHint` art, and every desktop body <= 90 characters for all nine key-scheme pairs), `guideSlice.test.ts` (this app's binding; `LEGACY_STORAGE_KEYS` non-empty and `lightcycles.`-namespaced; `createReturningPlayerMigrate` over each legacy key gives `GUIDE_VERSION` and no keys gives 0, also through real redux-persist; the real `persistConfig` has the migrate). The pager/dialog/provider/slice behavior is covered in `@tastic/hud`'s own suite. **Not verified live:** the card under a rotated (fake-landscape) hold. `GuideHost` passes `useRotation(...)` as the provider's `rotation`, and hud's `getGuideCardSize` swaps the card's axes for a quarter turn (unit-tested there), but nobody has held a real device sideways on Home yet.
- **hud source:** `createReturningPlayerMigrate` and `SeatDevicesHint` shipped in the published `@tastic/hud@0.13.0` (2026-09-25). The guide was first developed against a `yalc link` of the local hud build. That link was removed on 2026-10-01 (`yalc remove --all`, with `package.json` and `package-lock.json` unchanged), so this app no longer uses yalc for any package: there is no `.yalc/` and no `yalc.lock`. Never `yalc push` from hud: it rewrites every project registered in yalc's store, not just this one.
